## Abstract

This document specifies the standardized tool catalog for the Agent Telephony Protocol (ATP). It defines the canonical tool names (`phone.dial`, `sms.send`, `numbers.provision`, etc.), the JSON Schema shapes for each tool's arguments and results, the asynchronous "start + subscribe" pattern that lets long-running telephony operations operate within MCP's synchronous tool model, the common error envelope, and the conformance requirements per tool group. ATP-3 is the single most-cited RFC in the series — every implementation references it, every Agent codes against it, and every other channel-specific RFC (ATP-6 for voice tools, ATP-11 for messaging tools, etc.) elaborates the behavioral semantics of tools introduced here.

## 1. Introduction

Implementations of the Agent Telephony Protocol expose tools — discoverable, callable units of functionality — through the underlying MCP transport's `tools/list` and `tools/call` methods. For ATP to deliver portability across gateways and predictability for agent code, the tool names, argument shapes, and behavioral semantics must be standardized.

This RFC defines that standardization. It draws the line between *naming conventions* (which are mandatory for cross-gateway compatibility) and *operational semantics* (which are mandatory per channel-specific RFCs).

The canonical tool catalog has 35+ tools across nine namespaces (`phone.*`, `calls.*`, `messages.*`, `sms.*`, `otp.*`, `conversations.*`, `numbers.*`, `brands.*`, `kya.*`, `evidence.*`, `pricing.*`, `account.*`, `usage.*`). Not every gateway implements every tool; conformance tiers (per ATP-33) specify which subsets must be present at each tier.

---

## 2. Terminology

In addition to terms from ATP-1 and ATP-2:

- **Tool** — A named, callable function exposed by a Gateway and discoverable via MCP `tools/list`. Each tool has a name, an input schema (JSON Schema), and a result schema.
- **Tool group** — A set of tools sharing a namespace prefix and a common behavioral domain (e.g., all `phone.*` tools belong to the "voice control" group).
- **Result handle** — An identifier returned by a tool that initiated a long-running operation; the handle is used to subscribe to events or retrieve subsequent state.
- **Subscription tool** — A tool whose result is a stream of events (e.g., `calls.tail`), implemented via MCP's notification/streaming mechanisms rather than a single response.

## 3. Tool namespace conventions

### 3.1 Naming format

Tool names use `dot.separated.snake_case`:

- Lower case ASCII letters, digits, dots, and underscores only.
- One or more dot-separated namespace segments followed by an operation name.
- Each segment uses `snake_case` (lowercase, underscores, no hyphens or camelCase).
- Total length MUST NOT exceed 64 characters.

Regular expression: `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`

Examples: `phone.dial`, `calls.send_message`, `messages.wait_for`, `numbers.provision`.

### 3.2 Canonical namespaces

| Namespace | Domain | Detailed semantics in |
|---|---|---|
| `phone.*` | Voice call lifecycle control | ATP-6 |
| `calls.*` | Call resource queries + observation | ATP-6, ATP-5 |
| `messages.*` | Channel-abstract send/receive | ATP-11 |
| `sms.*` | SMS-specific convenience wrappers | ATP-11 |
| `otp.*` | One-time-password convenience wrappers | ATP-11 |
| `conversations.*` | Cross-channel conversation queries + observation | ATP-15 |
| `numbers.*` | Number provisioning, porting, release | ATP-19 |
| `brands.*` | Brand registration and lookup | ATP-20 |
| `kya.*` | KYA cert issuance, verification, revocation | ATP-22 |
| `evidence.*` | Evidence pack export | ATP-26 |
| `pricing.*` | Cost estimation | ATP-30 |
| `account.*` | Tenant-level account queries | (informational; this RFC) |
| `usage.*` | Usage reporting | (informational; this RFC) |

Implementations MAY define tools under additional namespaces but MUST NOT shadow or override the canonical namespaces above.

### 3.3 Tool name stability

Once a tool name appears in a published ATP RFC at status `draft-NN` or higher, the name is reserved. Renaming requires a successor RFC and a deprecation period of at least one MAJOR version. Implementations MAY support both the old and new names during deprecation.

## 4. Argument and result conventions

### 4.1 Common argument fields

The following argument fields appear across many tools and have consistent semantics:

| Field | Type | Meaning |
|---|---|---|
| `agent_id` | string | The Agent on whose behalf the operation is performed. OPTIONAL — defaults to the calling Agent if the session is per-Agent scoped. |
| `tenant_id` | string | The Tenant scope. OPTIONAL in `multi-tenant-shared` sessions (derived from auth); REQUIRED in `single-tenant` cross-tenant verification flows. |
| `idempotency_key` | string | Per §7. Caller-supplied unique key for safe retry. |
| `metadata` | object | Free-form key/value pairs, echoed back in the result and in subsequent events. Implementations MUST NOT interpret metadata semantically. |

Tools MUST NOT define their own argument fields named `agent_id`, `tenant_id`, `idempotency_key`, or `metadata` with semantics different from those above.

### 4.2 Common result fields

Every tool result is a JSON object. Long-running tools return a result handle (§5); short-running tools return the relevant resource representation. Common result fields:

| Field | Type | Meaning |
|---|---|---|
| `request_id` | string | Echoed from the MCP request `id`; useful for audit cross-reference. |
| `idempotency_key` | string | Echoed if supplied in the request. |
| `metadata` | object | Echoed from the request. |

### 4.3 Pagination

List-style tools (`calls.list`, `messages.list`, etc.) MUST follow the cursor-based pagination convention:

```json
{
  "items": [ /* page of results */ ],
  "page_size": 50,
  "next_cursor": "opaque-string-or-null"
}
```

The caller passes `cursor` and `page_size` arguments; `cursor` is opaque and MUST be passed verbatim from a previous `next_cursor`. Page sizes are clamped to gateway-defined ranges (RECOMMENDED: 1-200, default 50).

### 4.4 Filtering

List tools accept filter arguments specific to each tool. Filter arguments are AND-composed: the result set is the intersection of all filter matches. Filters MUST NOT use OR semantics within a single tool call.

## 5. The start + subscribe pattern

### 5.1 The challenge

Telephony operations are inherently long-running:

- A phone call lasts 30 seconds to 30 minutes.
- An SMS conversation may span days.
- An OTP wait may take 5-60 seconds.
- A number provisioning may take seconds (pool allocation) or weeks (international port).

MCP tools, by design, return a single result per call. Blocking a tool call for the duration of a 10-minute phone conversation is unworkable: connection pools exhaust, transport timeouts trigger, transient client failures lose results.

### 5.2 The pattern

ATP resolves this by mandating the **start + subscribe** pattern for all long-running operations:

```
Step 1: Agent calls a "start" tool.
        Tool returns IMMEDIATELY with a result handle (resource identifier).

Step 2: Agent subscribes to events for that resource via a "tail" or "wait" tool,
        or via webhook callback registered out-of-band.

Step 3: State changes flow as ATP events (per ATP-5 for calls, ATP-11 for messages)
        on the subscription. Final state is also retrievable on demand via `*.get` tools.
```

Example flow for an outbound call:

```
Agent → tools/call phone.dial({ to: "+14155550987", intent: "...", ... })
Gateway ← { call_id: "call_abc123", status: "queued", ... }    [immediate]

Agent → tools/call calls.tail({ call_id: "call_abc123", follow: true })
Gateway ← streaming events:
   event: call.queued     { call_id, dispatched_at }
   event: call.ringing    { call_id, attestation }
   event: call.answered   { call_id, answered_at }
   event: call.user_speaking
   event: call.user_partial { text: "Hello?" }
   ...
   event: call.ended      { call_id, reason: "remote_hangup", duration_sec: 87 }
   event: call.evidence_ready { evidence_pack_url, signature }
```

### 5.3 Tools that follow start + subscribe

| Start tool | Returns handle of type | Subscribe tool |
|---|---|---|
| `phone.dial` | `Call` | `calls.tail` |
| `phone.transfer` | `Call` (modified) | `calls.tail` |
| `messages.send` | `Message` | `conversations.tail` or per-message status query |
| `sms.send` | `Message` | same |
| `numbers.provision` | `Number` (immediate) or operation_id (deferred) | `numbers.get` polling |
| `numbers.port_in` | `Number` (with pending status) | `numbers.get` polling |
| `kya.issue` | `KYACert` | (none; certs are immediately final) |
| `evidence.export` | `EvidencePack` or async export_id | `evidence.export_status` polling |

Tools NOT in this table return their final result synchronously (e.g., `calls.get`, `pricing.quote`, `kya.verify`, `account.health`).

### 5.4 Tools that wait

A subset of subscription tools are "wait" tools — they suspend the calling tool call until either a matching event arrives or a timeout fires. `messages.wait_for` and `otp.wait_for` are the canonical examples.

Wait tools MUST accept a `timeout_sec` argument (max value gateway-defined, RECOMMENDED: 300). On timeout, the tool result MUST indicate `matched: false` and contain partial information about what was observed during the wait.

### 5.5 Subscription cancellation

An Agent cancels a subscription by closing the MCP stream associated with the subscription tool's response. Gateways MUST stop emitting events for that subscription within 5 seconds of the close.

The underlying long-running operation (e.g., the phone call itself) is NOT cancelled by subscription cancellation — only the event delivery to that one Agent. The call continues; the Gateway continues emitting events to any other subscribers and to the audit log.

To cancel the underlying operation, use the corresponding cancel tool (`phone.hangup`, `messages.cancel`, etc.).

## 6. Error envelope

### 6.1 Tool-level error format

Tool execution errors use the MCP `isError: true` mechanism, with the error payload conforming to the ATP error envelope:

```json
{
  "isError": true,
  "content": [
    {
      "type": "text",
      "text": "{ \"code\": -32101, \"message\": \"TCPA opt-out registry contains recipient number\", \"data\": { \"atp_error_symbol\": \"tcpa_optout\", \"to\": \"+14155550987\", \"opt_out_recorded_at\": \"2025-11-03T14:23:09Z\" } }"
    }
  ]
}
```

The JSON inside `content[0].text` is the ATP error envelope, with the same shape as the JSON-RPC error model defined in ATP-2 §10.

### 6.2 Canonical tool-execution error codes

These are tool-level errors per ATP-2 §10.1 (code range -32100 to -32999):

| Code | Symbol | When |
|---|---|---|
| -32100 | `tcpa_optout` | Recipient is in the opt-out registry per ATP-27 |
| -32101 | `quiet_hours` | Current time is outside the recipient's permitted calling window |
| -32102 | `consent_invalid` | Consent receipt missing, expired, or malformed per ATP-23 |
| -32103 | `consent_mismatch` | Consent receipt was issued for a different recipient or intent |
| -32104 | `number_not_provisioned` | The `from` number is not owned by the calling Tenant |
| -32105 | `number_capability_unavailable` | Number cannot send/receive on the requested channel |
| -32106 | `tier_unavailable` | The requested voice tier is not available for this number/jurisdiction |
| -32107 | `quota_exceeded` | Per-tenant or per-agent quota or budget exhausted (per ATP-31) |
| -32108 | `mandate_invalid` | The supplied mandate id is unknown or revoked |
| -32109 | `attestation_signing_failed` | STIR/SHAKEN or KYA cert could not be obtained from upstream authority |
| -32110 | `cpaas_provider_failure` | Downstream CPaaS provider returned an error |
| -32111 | `channel_unsupported_for_recipient` | Recipient device does not support the requested channel (e.g., RCS unavailable) |
| -32112 | `rate_limited` | Per-tenant or per-agent rate limit triggered |

Each error MUST include in `data` any operationally-relevant context (the offending field, the violated limit, the upstream provider's response, etc.) to enable both human and Agent debugging.

### 6.3 Error retryability

Errors carry a `retryable` field in `data` when retry semantics are ambiguous:

- `data.retryable: false` — the same call will fail again; do not retry.
- `data.retryable: true` — the call MAY succeed on retry, possibly after a delay; `data.retry_after_sec` may be provided.

`rate_limited` errors are always retryable with `retry_after_sec`. `tcpa_optout`, `consent_invalid`, `mandate_invalid` are never retryable.

## 7. Idempotency

### 7.1 Idempotency keys

Long-running and side-effecting tools (every tool that creates a Call, Message, or Number, or issues a KYACert or evidence export) MUST accept an `idempotency_key` argument.

The `idempotency_key`:

- Is a caller-chosen string of 8-64 alphanumeric, hyphen, or underscore characters.
- Is scoped to the (Tenant, tool, idempotency_key) triple.
- Has Gateway-defined retention (RECOMMENDED: minimum 24 hours).

### 7.2 Idempotency semantics

When a tool is called twice with the same `(tenant, tool, idempotency_key)` triple:

- If the first call is still in progress, the second call MUST wait for the first to complete and return its result.
- If the first call completed successfully, the second call MUST return the same result with no side effects.
- If the first call completed with an error, the second call MUST return the same error.

This prevents double-dialing, duplicate SMS sends, and duplicate number provisioning when a client retries due to a network failure.

### 7.3 Read tools

`*.get`, `*.list`, `pricing.quote`, `kya.verify`, and other read-only tools are naturally idempotent and SHOULD NOT require an idempotency key.

## 8. The canonical tool catalog

This section enumerates every standardized tool. Each entry lists arguments, returns, semantics, and the RFC where full behavioral semantics are defined.

### 8.1 `phone.*` — voice call control

#### `phone.dial`

Initiate an outbound voice call.

**Arguments:**

```json
{
  "to": "+14155550987",
  "from": "num_4155550123",
  "intent": "Confirm appointment at SuperCuts for Tuesday 2pm",
  "consent_receipt": "<base64url-encoded ATP-23 consent envelope>",
  "voice_tier": "standard",
  "guardrails": {
    "max_duration_sec": 600,
    "deny_topics": [],
    "require_human_handoff_on": []
  },
  "metadata": {},
  "idempotency_key": "appt-conf-2026-05-23-abc"
}
```

**Returns:**

```json
{
  "call_id": "call_abc123",
  "status": "queued"
}
```

Full semantics: ATP-6.

#### `phone.transfer`

Transfer an in-progress call to another destination (number, queue, or agent).

**Arguments:** `{ call_id, to, mode: "warm" | "cold" | "blind", context }`

**Returns:** updated `Call` resource representation.

Full semantics: ATP-6 (intra-channel transfer) and ATP-28, ATP-29 (cross-agent transfer).

#### `phone.hangup`

Terminate an in-progress call.

**Arguments:** `{ call_id, reason }`

**Returns:** `{ call_id, status: "ended" }`

#### `phone.hold`

Place an in-progress call on hold or take it off hold.

**Arguments:** `{ call_id, hold: true | false }`

#### `phone.dtmf`

Send DTMF digits on an in-progress call.

**Arguments:** `{ call_id, digits: "1234#" }`

### 8.2 `calls.*` — call queries and observation

#### `calls.list`

List calls matching filters.

**Arguments:** `{ since?, until?, status?, agent_id?, cursor?, page_size? }`

**Returns:** paginated `Call` list per §4.3.

#### `calls.get`

Retrieve a single call's current state.

**Arguments:** `{ call_id }`

**Returns:** `Call` resource.

#### `calls.tail`

Subscribe to live events for a call.

**Arguments:** `{ call_id, follow: true | false, since_seq?, mode: "observe" | "inject" }`

**Returns:** event stream per ATP-5.

`mode` defaults to `observe`. `inject` permits subsequent `calls.send_message` calls on this call from this subscription.

#### `calls.send_message`

Inject a text turn into a live call (the call's gateway-side TTS speaks the injected text). Requires that a prior `calls.tail` with `mode: "inject"` is active.

**Arguments:** `{ call_id, text, mode: "tts" | "whisper" }`

`whisper` (where supported by the underlying telephony) addresses only the calling Agent's runtime, not the remote party.

#### `calls.takeover`

Hand off the in-call LLM responsibility from the Gateway's hosted driver to the caller (the Smart Observer). Requires that the Gateway supports takeover (advertised in capabilities); full semantics in ATP-6.

**Arguments:** `{ call_id, handoff_envelope_id? }`

**Returns:** `{ call_id, takeover_complete: true | false, audio_stream_url? }`

### 8.3 `messages.*` — channel-abstract messaging

#### `messages.send`

Send a message on one or more channels with declarative fallback.

**Arguments:**

```json
{
  "from": "num_4155550123",
  "to": "+14155550987",
  "body": "Your appointment is confirmed.",
  "preferred_channels": ["rcs", "sms"],
  "fallback_timeout_sec": 30,
  "rich_content": null,
  "media_url": [],
  "metadata": {},
  "idempotency_key": "appt-conf-msg-001"
}
```

**Returns:** `{ message_id, conversation_id, channel_used, status }`

Full semantics: ATP-11, ATP-12 (rich content), ATP-13 (fallback rules).

#### `messages.list`

**Arguments:** `{ number_id?, conversation_id?, since?, channel?, cursor?, page_size? }`

#### `messages.wait_for`

Long-poll for an inbound message matching a pattern.

**Arguments:** `{ number_id, contains_pattern?, source_pattern?, timeout_sec }`

**Returns:** `{ matched: true | false, message? }`

### 8.4 `sms.*` — SMS convenience wrappers

#### `sms.send`

Convenience wrapper for SMS-only sends. Equivalent to `messages.send` with `preferred_channels: ["sms"]`.

**Arguments:** `{ from, to, body, metadata?, idempotency_key? }`

### 8.5 `otp.*` — OTP convenience wrappers

#### `otp.wait_for`

Convenience wrapper around `messages.wait_for` with a regex hint suited to OTPs.

**Arguments:** `{ number_id, pattern?, source_pattern?, timeout_sec }`

**Returns:** `{ matched: true | false, code?, message? }`

Default `pattern` is `\b\d{4,8}\b` if not supplied. `code` is the first regex group that matches.

### 8.6 `conversations.*` — cross-channel threads

#### `conversations.list`

**Arguments:** `{ participant?, tenant_id?, channel?, open_only?, cursor?, page_size? }`

#### `conversations.get`

**Arguments:** `{ conversation_id }`

#### `conversations.tail`

Subscribe to events across all channels in a conversation.

**Arguments:** `{ conversation_id, follow, since_seq? }`

Full semantics: ATP-15.

### 8.7 `numbers.*` — number provisioning

#### `numbers.provision`

**Arguments:**

```json
{
  "country": "US",
  "area_code": "415",
  "capabilities": ["voice", "sms"],
  "use_case": "appointment-confirmation",
  "tier": "standard",
  "idempotency_key": "provision-2026-05-23-001"
}
```

**Returns:** `Number` resource (immediate) or `{ operation_id, status: "pending" }` for deferred provisioning (e.g., international or specialized capabilities).

Full semantics: ATP-19.

#### `numbers.list`

**Arguments:** `{ capability?, country?, cursor?, page_size? }`

#### `numbers.release`

**Arguments:** `{ number_id }`

**Returns:** `{ number_id, status: "released" }`

#### `numbers.port_in`

**Arguments:** `{ e164, current_carrier, port_loa_url, requested_port_date? }`

**Returns:** `{ number_id, status: "pending_port", port_id }`

### 8.8 `brands.*` — verified business identity

#### `brands.register`

**Arguments:** `{ legal_entity_name, ein, jurisdiction, vertical, contact, idempotency_key }`

**Returns:** `Brand` resource.

#### `brands.get`

**Arguments:** `{ brand_id }`

Full semantics: ATP-20.

### 8.9 `kya.*` — Know Your Agent attestation

#### `kya.issue`

(Issuer-side tool.) Issue a new KYA cert for an Agent.

**Arguments:** `{ agent_id, expires_at?, optional_claims? }`

**Returns:** `KYACert` resource including the signed CWT envelope.

#### `kya.verify`

(Verifier-side tool.) Verify a KYA cert.

**Arguments:** `{ kya_cert: "<base64url COSE_Sign1>" }`

**Returns:** `{ valid: true | false, claims?, reason? }` per ATP-22 §6.

#### `kya.revoke`

(Issuer-side tool.) Add a `cti` to the revocation list.

**Arguments:** `{ kya_cert_id, reason }`

Full semantics: ATP-22.

### 8.10 `evidence.*` — audit and compliance export

#### `evidence.export`

**Arguments:** `{ scope: { call_id? | conversation_id? | date_range? }, schema, idempotency_key }`

**Returns:** `EvidencePack` resource (immediate for small scopes) or `{ export_id, status: "pending" }`.

Full semantics: ATP-26.

#### `evidence.export_status`

**Arguments:** `{ export_id }`

**Returns:** `{ status: "pending" | "ready" | "failed", evidence_pack? }`

### 8.11 `pricing.*` — cost discovery

#### `pricing.quote`

**Arguments:** `{ spec: { call? | message? }, currency? }`

**Returns:** `{ estimated_cost: { amount_minor_units, currency }, breakdown: [...] }`

Full semantics: ATP-30.

### 8.12 `account.*` — Tenant queries

#### `account.get`

**Arguments:** none (uses session's authenticated Tenant).

**Returns:** Tenant resource representation.

#### `account.health`

**Arguments:** none.

**Returns:** `{ overall: "ok" | "degraded" | "down", components: [...] }`

### 8.13 `usage.*` — usage reporting

#### `usage.get`

**Arguments:** `{ period: { since, until }, group_by?: "agent" | "number" | "channel" }`

**Returns:** structured usage report including minutes, message counts, costs per group.

## 10. Open issues for review

### 10.1 Tool name future-proofing

§3.1 caps tool names at 64 characters. As ATP grows, deeply nested namespaces could exceed this. Should v2 raise the limit, or enforce a maximum nesting depth (e.g., max 3 dots) instead?

### 10.2 Argument schema versioning

Tool argument schemas may evolve. Currently the spec requires backward-compatible additions only (per ATP-1 §9 MINOR versioning rules). Should individual tools carry their own version number for finer-grained compatibility tracking?

### 10.3 Webhook vs subscription

§5 mandates start + subscribe via in-session events. Some agent deployments cannot maintain a long-lived event stream (e.g., serverless functions). Should ATP-3 also normatively define a webhook callback mechanism as a permitted alternative to subscription? Currently webhook usage is implementation-defined.

### 10.4 Idempotency-key collisions across agents

§7.1 scopes idempotency to (Tenant, tool, idempotency_key). Two Agents under the same Tenant cannot use overlapping keys. Should keys be scoped to (Tenant, Agent, tool, idempotency_key) instead?

### 10.5 Cancellation of `wait_for` and `tail`

§5.5 specifies that closing the MCP stream cancels the subscription. Some MCP transport bindings (e.g., stdio) may not have an unambiguous "close stream" notion. Should a `subscription_id` and explicit `*.cancel` tool be added for transport-portability?

### 10.6 Error code -32109 (`attestation_signing_failed`) granularity

This error covers both STIR/SHAKEN and KYA cert failures. Production debugging may need finer distinctions. Split into multiple codes in v2?

### 10.7 `calls.takeover` audio handoff

§8.2 describes `calls.takeover` returning an optional `audio_stream_url`. The exact URL form and audio stream protocol are TBD (per ATP-9 in Phase 3). v1 implementations of takeover are text-only.

### 10.8 Bulk operations

This RFC defines per-resource tools. Bulk operations (e.g., "release these 50 numbers") are not specified — callers loop. Should v2 add bulk variants for high-volume tenants?
