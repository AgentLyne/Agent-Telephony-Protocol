## Abstract

This document specifies the session model for the Agent Telephony Protocol (ATP): how Agents and Gateways establish a session, advertise capabilities, authenticate, negotiate the protocol version, address multi-tenancy, and select among the available transport bindings (stdio, HTTP, HTTP+SSE, WebSocket). ATP-2 extends the Model Context Protocol's (MCP) `initialize` handshake with an `atp_capabilities` advertisement block. It also normatively defines the durability requirements that allow long-running telephony resources (live calls, open SMS conversations) to survive client disconnections and reconnections.

## 1. Introduction

The Model Context Protocol (MCP, Anthropic, November 2024) defines a session model in which an Agent (client) and a Gateway (server) exchange an `initialize` request and response to establish a connection, advertise capabilities, and begin tool calls and resource reads. MCP's base session model is sufficient for stateless tool servers and short-lived agent interactions, but it does not by itself address:

- The set of telephony-specific capabilities an ATP Gateway advertises
- The transport requirements that telephony-grade event streaming (per ATP-5) and audio streaming (per ATP-9) impose
- How long-running telephony resources (live calls, open conversations) survive Agent disconnection
- How multi-tenant Gateways scope authentication, configuration, and resources per Tenant

ATP-2 closes these gaps by layering on MCP. An ATP-conforming session is, by construction, an MCP-conforming session — Agents that speak MCP without ATP can still connect to an ATP Gateway and receive its non-telephony capabilities; ATP-aware Agents additionally discover and use the telephony surface.

---

## 2. Terminology

In addition to the terms defined in ATP-1, this RFC uses:

- **Session** — A logical communications channel between an Agent and a Gateway, initiated by an MCP `initialize` request and terminated by either party closing the underlying transport. A session has at most one open transport at a time.
- **Transport** — The wire-level protocol carrying MCP messages. ATP recognizes four: stdio, HTTP (request/response), HTTP+SSE (streaming responses + server-sent events), and WebSocket.
- **Capability** — A discrete behavior an Agent or Gateway implements, advertised in the session handshake. ATP capabilities are identified by RFC number (e.g., "this Gateway implements ATP-22") or by named feature flag.
- **Tenant scope** — The constraint that all resources, tools, and events surfaced in a session are bound to a specific Tenant identifier. Tenant scope is established by the session's authentication credentials.
- **Tenancy mode** — One of `single-tenant` (the Gateway endpoint serves exactly one Tenant per deployment), `multi-tenant-shared` (one endpoint serves many Tenants, scoped by auth), or `multi-tenant-routed` (per-Tenant hostnames or URL paths route to per-Tenant services).

RFC 2119 / RFC 8174 requirements language applies.

## 3. Session model

### 3.1 Session lifecycle

An ATP session progresses through three states:

```
                ┌──────────────────┐
                │   uninitialized  │
                └────────┬─────────┘
                         │ Agent → MCP initialize request
                         │ (with atp_capabilities)
                         ▼
                ┌──────────────────┐
                │     handshaking  │
                └────────┬─────────┘
                         │ Gateway → MCP initialize response
                         │ (with atp_capabilities advertised)
                         ▼
                ┌──────────────────┐
                │       ready      │ ◄───── tool calls, resource reads,
                └────────┬─────────┘        notifications, events
                         │
                         │ transport close (either party)
                         ▼
                ┌──────────────────┐
                │      closed      │
                └──────────────────┘
```

A session in the `ready` state remains usable for the lifetime of the underlying transport. Sessions are not durable; closing the transport closes the session. Resources owned by the Tenant outlive the session (see §9).

### 3.2 Session identity

Each session has a `session_id` assigned by the Gateway during the `initialize` response. The Gateway's `session_id` MUST be unique within the Gateway across all concurrent and past sessions. Implementations are RECOMMENDED to use a UUID v4 or equivalent.

The `session_id` is used in audit logs (ATP-25) and as the join key for tool calls and events within a session.

### 3.3 Session-bound versus tenant-bound state

ATP distinguishes:

- **Session-bound state** — transient configuration relevant only for the duration of the session (e.g., the set of tools currently subscribed for streaming notifications).
- **Tenant-bound state** — persistent resources owned by the Tenant (e.g., Numbers, Agents, Calls in progress, Messages received). Tenant-bound state survives session closure and is reattached on reconnection.

All ATP resources defined in §5 of ATP-1 are tenant-bound. No resource is session-bound.

## 4. The ATP `initialize` extension

### 4.1 Request format

An ATP-aware Agent extends MCP's `initialize` request with an `atp` capability block:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "atp": {
        "atp_version_range": ["0.1", "0.1"],
        "rfcs_required": [1, 2, 3],
        "rfcs_optional": [4, 5, 6, 10, 11, 22],
        "transports_supported": ["http+sse", "websocket"],
        "tenancy_mode_preferred": "multi-tenant-shared",
        "max_concurrent_calls": 100
      },
      "tools": {},
      "resources": {}
    },
    "clientInfo": {
      "name": "agentlyne-mcp-reference-client",
      "version": "0.1.0"
    }
  }
}
```

### 4.2 Response format

The Gateway responds with its own `atp` block describing what it actually implements:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "atp": {
        "atp_version_selected": "0.1",
        "rfcs_implemented": [1, 2, 3, 4, 5, 6, 7, 10, 11, 13, 14, 18, 19, 22, 23, 24, 25],
        "transports_active": ["http+sse"],
        "tenancy_mode_active": "multi-tenant-shared",
        "channels_supported": ["voice", "sms", "mms"],
        "voice_tiers_supported": ["economy", "standard"],
        "conformance_tier": "+identity",
        "evidence_pack_schemas": ["raw_audit_v1"],
        "max_concurrent_calls": 1000,
        "session_id": "ses_8a3f9b2e7c1d4506",
        "gateway_did": "did:web:agentlyne.ai"
      }
    },
    "serverInfo": {
      "name": "agentlyne-gateway",
      "version": "0.1.0"
    }
  }
}
```

### 4.3 Negotiation outcome

The negotiation outcome is the intersection of Agent and Gateway capabilities:

- **`atp_version_selected`** — the highest MAJOR.MINOR version present in both the Agent's `atp_version_range` and the Gateway's supported range. If no overlap exists, the Gateway MUST respond with `error.code = -32000` and a human-readable message (§10).
- **`rfcs_implemented`** — the Gateway's actual implementation set. The Agent SHOULD check that all RFCs in its `rfcs_required` list appear here; if not, the Agent SHOULD close the session with an appropriate error notification.
- **`transports_active`** — the transport(s) the Gateway exposes for this session. The Agent uses these for subsequent requests within the session.

## 5. Capability advertisement

### 5.1 Capability identifiers

ATP capabilities are identified in three ways:

1. **By RFC number** — the most common form. Lists the ATP RFCs the implementation conforms to (e.g., `rfcs_implemented: [1, 2, 3, 22]`).
2. **By named feature flag** — for sub-features within an RFC that some implementations may omit (e.g., `voice_tiers_supported: ["economy", "standard", "premium"]`; `channels_supported: ["voice", "sms", "rcs"]`).
3. **By conformance tier** — a shorthand for a combination of RFCs (defined in ATP-33). Permitted values: `basic`, `+identity`, `+evidence-pack`, `+cross-channel`, `+realtime-audio`, `+operational`.

### 5.2 Capability semantics

Capability advertisement is informational, not contractual. A Gateway advertising a capability MUST support the corresponding behavior; an Agent invoking a non-advertised capability MUST receive an appropriate error (§10).

Capability presence does not imply capability availability. A Gateway that advertises voice support but is experiencing a CPaaS outage SHOULD still advertise the capability and return per-call errors when calls fail.

### 5.3 Required capability set for any ATP session

Every ATP-conforming session implements at least: ATP-1 (this terminology), ATP-2 (this session model), ATP-3 (tool catalog conventions). A Gateway advertising any of `rfcs_implemented` MUST include `[1, 2, 3]` in that list.

### 5.4 Capability discovery without atp_capabilities

An MCP client that does not understand the `atp` capability block can still call ATP tools by name (`phone.dial`, etc.) using standard `tools/call`. The Gateway MUST surface ATP tools in the standard MCP `tools/list` response, with namespacing per ATP-3.

## 6. Transport bindings

### 6.1 Defined transports

ATP recognizes four transports:

| Transport | MCP support | ATP use |
|---|---|---|
| **stdio** | MCP base | Local agent-to-gateway communication (rare for production telephony, useful for development) |
| **HTTP** (request/response) | MCP base | One-shot tool calls, resource reads, configuration |
| **HTTP+SSE** | MCP base | Event streaming for ATP-5 (call events), `calls.tail`, `messages.wait_for`, `conversations.tail` |
| **WebSocket** | MCP extension | Bidirectional streaming required by ATP-9 (audio streaming) and recommended for high-throughput event delivery |

### 6.2 Transport requirements per conformance tier

| Conformance tier | MUST support | SHOULD support |
|---|---|---|
| `basic` | HTTP, HTTP+SSE | stdio |
| `+identity` | HTTP+SSE | WebSocket |
| `+evidence-pack` | HTTP+SSE | WebSocket |
| `+cross-channel` | HTTP+SSE, WebSocket | — |
| `+realtime-audio` | WebSocket | — |
| `+operational` | HTTP+SSE | WebSocket |

Implementations claiming a tier MUST support every transport in that tier's "MUST" column.

### 6.3 Selection algorithm

When multiple transports are jointly supported, the negotiated transport SHOULD be:

1. **WebSocket** if both parties support it AND the session expects real-time event volume above ~10 events/second (e.g., voice calls with partial transcripts) OR ATP-9 audio streaming.
2. **HTTP+SSE** otherwise, when both parties support it and event streaming is expected.
3. **HTTP** for stateless or low-volume interaction.
4. **stdio** only for in-process / local-process deployments.

The negotiated transport is communicated in the `transports_active` field of the `initialize` response (§4.2).

### 6.4 Transport upgrade

A session that begins on one transport MAY upgrade to another mid-session (e.g., HTTP+SSE → WebSocket when an audio stream is initiated). The mechanism for upgrade is transport-specific and defined in transport-binding subsections of ATP-9 (for the audio case) or by the implementation (for other cases).

## 7. Authentication and tenancy

### 7.1 Authentication mechanisms

ATP Gateways exposing HTTP, HTTP+SSE, or WebSocket transports MUST support **Bearer token** authentication carried in the `Authorization` HTTP header per RFC 6750. The token is opaque to ATP — the format and issuance are determined by the Gateway operator.

ATP Gateways exposing ONLY the stdio transport (in-process Gateways, controlled-subprocess deployments, local development setups) MAY rely on process-level authentication (the controlling parent process has already authorized the Agent by spawning it) and need not implement Bearer token support. Gateways exposing stdio over network boundaries (e.g., tunneled through SSH, exposed via socket) MUST require authentication via a method appropriate to the transport.

ATP Gateways SHOULD support **OAuth 2.1** flows for use cases requiring user-delegated access (e.g., an Agent acting on behalf of a human end-user who has granted scoped permissions).

ATP Gateways MAY support other authentication mechanisms (mutual TLS, signed JWTs, hardware tokens) per implementation policy.

### 7.2 Tenant scope

Every authenticated session is bound to exactly one Tenant. The Tenant identifier MUST be derivable from the authentication credentials. Three derivation modes are permitted:

- **`token-claim`** — the bearer token (typically a signed JWT) contains a `tenant_id` claim.
- **`token-lookup`** — the Gateway maintains a token-to-Tenant mapping in its credential store; the token itself is opaque.
- **`header`** — for development or proxy scenarios, the Tenant may be supplied in an `X-ATP-Tenant` HTTP header alongside the bearer token. This mode SHOULD NOT be used in production.

### 7.3 Tenancy modes

A Gateway operates in one of three tenancy modes, advertised in `tenancy_mode_active`:

- **`single-tenant`** — the Gateway endpoint serves exactly one Tenant. Tenant scope is implicit; no `tenant_id` is required in tool arguments or resource paths.
- **`multi-tenant-shared`** — the Gateway endpoint serves many Tenants. Tenant scope is derived from authentication credentials (§7.2). Tool arguments and resource paths reference only the active Tenant's resources.
- **`multi-tenant-routed`** — per-Tenant hostnames or URL path prefixes route to per-Tenant configuration. Useful for white-label deployments. Functionally equivalent to single-tenant from the Agent's perspective once routing is resolved.

### 7.4 Cross-tenant references

Tool arguments and resource references in a session MUST NOT reference resources of a Tenant other than the session's active Tenant. Gateways MUST return an `error.code = -32001` (per §10) if a cross-tenant reference is detected.

The only exception is the verification flow for ATP-22 KYA certs: a Verifier in any Tenant scope may verify a cert issued for an Agent in any other Tenant scope, because verification operates over signed public claims rather than mutable resources.

## 8. Version negotiation

### 8.1 Algorithm

The negotiated `atp_version_selected` is computed as:

```
selected = max(intersection(agent.atp_version_range, gateway.atp_version_range))
```

Where intersection is performed on (MAJOR, MINOR) tuples lexicographically. If the intersection is empty, the session is rejected.

### 8.2 Forward compatibility

Within a MAJOR version, MINOR additions MUST be backward-compatible. A Gateway implementing ATP `0.2` MUST be able to serve an Agent that advertises `atp_version_range: ["0.1", "0.1"]` by serving the `0.1` subset.

### 8.3 Breaking changes

MAJOR version increments are reserved for breaking changes (e.g., the removal of a deprecated field, a change in default behavior that requires Agent updates). MAJOR transitions are anticipated to be rare — at most once per year.

### 8.4 RFC ratification level

An RFC's status (draft, working-group, ratified) is tracked in the spec repository, not in the version negotiation. Gateways MAY implement draft RFCs; Agents MAY consume them. Production deployments are RECOMMENDED to depend only on RFCs at the working-group or ratified level.

## 9. Session durability and reconnection

### 9.1 Resource persistence

ATP resources (Calls, Messages, Conversations, EvidencePacks, etc.) persist independently of any session. Closing or losing a session does NOT cancel an in-progress call, drop unread messages, or invalidate cached events.

### 9.2 Reconnection workflow

When an Agent reconnects after a session interruption:

1. The Agent initiates a new MCP session (§4).
2. The Agent retrieves currently-live resources via `calls.list`, `messages.list`, `conversations.list`, etc. (each with an `active_only: true` filter where applicable).
3. For any resource the Agent wishes to continue observing in real-time, the Agent re-subscribes via the appropriate streaming tool (`calls.tail`, `messages.wait_for`, `conversations.tail`), passing a `since_seq` parameter to resume from the last received event sequence number.
4. The Gateway delivers all events with sequence numbers greater than `since_seq` from its retained event buffer.

### 9.3 Event buffer retention

Gateways MUST retain per-resource event streams for at least 5 minutes after the last subscriber disconnects. Gateways SHOULD retain longer (1 hour RECOMMENDED) to accommodate Agent crashes and restarts.

After retention expires, events are no longer replayable via `since_seq`. The most recent state is still available via `calls.get`, `messages.list`, etc., but the per-turn event sequence is lost.

### 9.4 Long-running tool calls

Tools that initiate long-running operations (e.g., `phone.dial`, `numbers.provision`) MUST return immediately with a resource identifier. State changes thereafter flow exclusively through the relevant event stream (per ATP-5, ATP-11). Implementations MUST NOT block the tool call response on completion of the underlying operation.

This is the "start + subscribe" pattern that makes telephony's inherent long-livedness compatible with MCP's synchronous tool model. ATP-3 specifies it in detail.

## 10. Error model

### 10.1 Error sources

Errors in ATP can arise from four sources, each with a distinct code range:

| Source | Code range | Examples |
|---|---|---|
| **Protocol** (JSON-RPC, MCP-level) | -32700 to -32600 | malformed request, unknown method |
| **Session** (ATP-2-specific) | -32000 to -32099 | version mismatch, auth failure, tenancy violation |
| **Tool execution** (per-tool semantic) | -32100 to -32999 | TCPA opt-out, invalid consent, quota exceeded |
| **Implementation** (Gateway-specific) | < -33000 | downstream provider outage, internal error |

### 10.2 Standard session errors

| Code | Symbol | Meaning |
|---|---|---|
| -32000 | `atp_version_unsupported` | No common version between Agent and Gateway |
| -32001 | `cross_tenant_reference` | Tool argument or resource reference points to another Tenant |
| -32002 | `auth_required` | Session lacks valid authentication |
| -32003 | `auth_invalid` | Authentication credentials are present but invalid |
| -32004 | `tenant_suspended` | Tenant exists but is suspended (billing, compliance, etc.) |
| -32005 | `rfc_not_implemented` | Tool, resource, or event refers to an RFC not in `rfcs_implemented` |
| -32006 | `session_expired` | Server-side session timeout; client should reinitialize |

### 10.3 Error payload format

```json
{
  "code": -32005,
  "message": "ATP-15 (Conversation Resource) not implemented by this gateway",
  "data": {
    "atp_error_symbol": "rfc_not_implemented",
    "rfc": 15,
    "documentation_url": "https://github.com/AgentLyne/Agent-Telephony-Protocol/blob/main/ATP-SPEC.md#3-canonical-rfc-list"
  }
}
```

The `documentation_url` field is OPTIONAL and provided as a Verifier convenience. Gateways MAY point it at the canonical RFC list (as shown), at the RFC's standalone file (e.g., `/rfcs/RFC-0015.md` once published), or at any other resolvable URL describing the referenced RFC.

The `data.atp_error_symbol` field is the machine-readable error identifier; `code` is the JSON-RPC integer code. Clients MAY rely on either.

## 11. Conformance considerations

A Gateway claims ATP-2 conformance by:

1. Implementing the `initialize` extension per §4.
2. Advertising at least the `basic` conformance tier's required transports per §6.2.
3. Supporting bearer-token authentication on any network-exposed transport per §7.1 (Gateways advertising only the `stdio` transport may rely on process-level authentication and need not implement Bearer; see §7.1).
4. Persisting resources across session closures per §9.1.
5. Buffering events per §9.3 retention requirements.
6. Surfacing errors per the §10 error model.

An Agent claims ATP-2 conformance by:

1. Sending a well-formed `atp` capability block in `initialize`.
2. Tolerating Gateway capability advertisements that include unrecognized fields.
3. Using `since_seq` when re-subscribing to event streams.
4. Handling all standard session errors (§10.2) gracefully.

## 12. Open issues for review

### 12.1 OAuth 2.1 normative status

§7.1 specifies Bearer tokens as MUST and OAuth 2.1 as SHOULD. Should v2 elevate OAuth 2.1 to MUST for the `+identity` tier and above, where user-delegated access is more likely to be required?

### 12.2 stdio production use

§6.2 marks stdio as optional. Some deployments (in-process agents in single-tenant gateways) may treat stdio as essential. Should ATP-2 add a dedicated `local-singleton` deployment mode that REQUIRES stdio?

### 12.3 Event buffer minimum

§9.3 sets 5-minute minimum retention. Stress testing in production deployments may reveal this is too low (agents that restart on a 10-minute schedule lose events) or too high (memory pressure on busy gateways). Calibrate from real-world data once available.

### 12.4 Tenancy mode `header` security

§7.2 permits `X-ATP-Tenant` header derivation but discourages it for production. Should v2 deprecate this mode entirely, or formalize the threat model under which it remains acceptable?

### 12.5 Multi-region session affinity

ATP-2 does not address geographic session affinity. A Gateway deployed across multiple regions may need to pin a session to one region for consistency (especially for the per-region event buffers in §9.3). Should this be addressed in ATP-2 or deferred to operational guidance?

### 12.6 Cross-session resource observation

ATP-2 binds events per session. An advanced use case is "fan out the same call's events to multiple concurrent agent sessions" (e.g., a primary agent + an audit/monitoring agent). Currently this is supported by both agents independently calling `calls.tail` on the same call. Should a more structured "observer" relationship be formalized?
