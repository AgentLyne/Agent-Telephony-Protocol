## Abstract

This document defines the architectural model, role taxonomy, resource type hierarchy, identifier formats, time and date encodings, naming conventions, and versioning policy used by every other RFC in the Agent Telephony Protocol (ATP) series. It is the foundational reference document of ATP. RFCs ATP-2 through ATP-35 normatively depend on the terms and conventions established here.

ATP-1 is intentionally short. It is the equivalent of the "Definitions" chapter that every RFC, ISO standard, and IETF Internet-Draft begins with. Subsequent RFCs are written assuming the reader has internalized this document.

## 1. Introduction

The Agent Telephony Protocol (ATP) is a protocol for AI agents to use the telephone network. ATP defines how agents discover telephony capabilities exposed by gateways, place and receive calls, send and receive messages on every modern channel, present verifiable operator identity, transfer conversations across runtimes, and produce auditable evidence for regulatory compliance regimes.

ATP is a sibling protocol to the Model Context Protocol (MCP, Anthropic, November 2024). ATP normatively references MCP 2025-03 or later for session initialization, capability advertisement, tool invocation, resource reading, and notification delivery. ATP adds the telephony-specific resources, events, schemas, attestation envelopes, and operational primitives that MCP intentionally omits.

ATP is structured as a series of 35 numbered RFCs, grouped into eight functional blocks plus a conformance block. The full series is described in [ATP-SPEC.md](../ATP-SPEC.md). This document, ATP-1, defines the foundational vocabulary that the remaining 34 RFCs reuse.

## 2. Terminology and conventions

### 2.1 Requirements language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when, and only when, they appear in all capital letters.

### 2.2 Reference notation

References to other ATP RFCs use the form "ATP-N" (e.g., "ATP-22 KYA"). References to external standards use the form "RFC NNNN" for IETF RFCs, the standard short name for ISO/W3C/ECMA documents, and the URL or DOI for other sources.

### 2.3 Spec versus implementation

ATP defines a *specification*. Implementations of ATP — gateways, MCP servers, SDKs, reference clients — are independent works subject to their own licensing terms. The behavioral requirements in ATP RFCs apply to implementations; the editorial conventions (formatting, language) apply only to spec documents.

## 3. Architectural overview

ATP defines a four-layer architecture spanning the AI agent, the ATP gateway, the carrier-grade telephony provider (CPaaS), and the public switched telephone network (PSTN) plus rich-messaging vendors.

```
┌────────────────────────────────────────────────────────────────────┐
│  Layer 1 — Agent runtime                                           │
│  Any MCP-speaking program: Anthropic Claude, OpenAI Agents SDK,    │
│  Cursor, Claude Code, OpenHands, Windsurf, custom.                 │
│  Speaks MCP base + ATP extensions.                                 │
└─────────────────────────────────┬──────────────────────────────────┘
                                  │ MCP session over stdio/HTTP/SSE/WebSocket
                                  ▼
┌────────────────────────────────────────────────────────────────────┐
│  Layer 2 — ATP gateway                                             │
│  Persistent service implementing ATP. Owns call sessions, message  │
│  inboxes, audit logs, KYA cert issuance, conversation state, and   │
│  credentials with downstream providers.                            │
│  Multi-tenant. Multi-CPaaS-capable.                                │
└──┬───────────────────────────┬──────────────────────────┬──────────┘
   │                           │                          │
   ▼                           ▼                          ▼
┌──────────────┐         ┌──────────────┐         ┌──────────────────┐
│  Layer 3a    │         │  Layer 3b    │         │  Layer 3c        │
│  CPaaS       │         │  Rich-msg    │         │  Identity        │
│  (Telnyx,    │         │  vendors     │         │  authorities     │
│  Twilio,     │         │  (WABA, RBM, │         │  (STI-AS,        │
│  Bandwidth,  │         │  Apple MfB,  │         │  TCR, ICANN-     │
│  Plivo, ...) │         │  GBM)        │         │  registered DNS, │
│  Voice + SMS │         │              │         │  KYA issuers)    │
└──────┬───────┘         └──────┬───────┘         └──────────────────┘
       │                        │
       ▼                        ▼
            ┌────────────────────────────────┐
            │  Layer 4 — PSTN + OTT channels │
            │  SIP, RTP, SS7, GSM, RCS,      │
            │  iMessage, WhatsApp networks   │
            └────────────────────────────────┘
```

Layers 1 and 2 are the principal subjects of ATP. Layer 3 is consumed by ATP gateways but not normatively constrained by ATP. Layer 4 is out of scope.

## 4. Roles

ATP defines six normative roles. Every entity in an ATP interaction acts as one or more of these roles.

### 4.1 Agent

An *Agent* is an AI runtime persona configured under a Tenant. An Agent has a persistent identity (an `agent_id`), a configurable persona (system prompt, voice tier, tool catalog, allowed call categories), and a Tenant of record. An Agent does not exist independently of a Tenant.

A single Tenant MAY operate many Agents. A single Agent MUST belong to exactly one Tenant.

### 4.2 Tenant

A *Tenant* is the legally accountable real-world entity that holds responsibility for one or more Agents. Tenants are natural persons, LLCs, corporations, or analogous structures under the jurisdiction's law. A Tenant is the boundary at which legal liability for Agent behavior is fixed.

A Tenant carries Know-Your-Customer (KYC) verification (see ATP-22 §4.2) that establishes its real-world existence and authorized representatives.

### 4.3 Gateway

A *Gateway* is a persistent network service that implements ATP. Gateways are the intermediaries between Agents and the public telephony network. A Gateway:

- Implements the ATP tool catalog (ATP-3) and event vocabulary (ATP-5)
- Holds credentials with one or more CPaaS providers (Layer 3a)
- Holds credentials with one or more rich-messaging vendors (Layer 3b) — OPTIONAL
- Operates KYA cert issuance (ATP-22), or partners with an external KYA Issuer
- Maintains per-Tenant audit logs (ATP-25)
- Exposes MCP server endpoints (per-Tenant or shared with auth-scoped tenancy)

Gateways MAY be operated by AgentLyne, by enterprises hosting their own ATP infrastructure, by open-source projects, or by other service providers. ATP is gateway-agnostic.

### 4.4 Carrier

A *Carrier* is a telephony service provider that operates SIP termination, SMS messaging, number provisioning, and STIR/SHAKEN signing. ATP refers to Carriers as CPaaS providers when speaking of their API-accessible surface (Telnyx, Twilio, Bandwidth, Plivo, Vonage, Sinch).

ATP gateways consume carrier services. ATP itself does not constrain carrier behavior.

### 4.5 Issuer

An *Issuer* is an entity authorized to issue ATP attestation envelopes (KYA certs per ATP-22). An Issuer asserts, by its signature on an attestation, that the bound claims are true to the best of its KYC-verified knowledge.

The Issuer role is partially overlapping with the Gateway role: an entity MAY operate as both a Gateway and an Issuer. AgentLyne is the initial reference Issuer (ATP-22 §5.4). Other entities MAY become Issuers per the requirements in ATP-22 §5.2.

### 4.6 Verifier

A *Verifier* is any entity that consumes and validates an ATP attestation envelope. Recipient gateways, recipient carriers, recipient applications, regulators, and the agents themselves can all act as Verifiers.

A Verifier MUST perform the verification algorithm defined in the relevant attestation RFC (e.g., ATP-22 §6 for KYA) before treating an attestation as authoritative.

## 5. Resource type hierarchy

ATP defines nine first-class resource types. Every persistent entity in an ATP system is one of these types. Each resource type is fully specified in the RFC indicated in the table; this RFC defines only their existence and identifier format.

| Resource | Defined in | Identifier prefix |
|---|---|---|
| **Tenant** | ATP-1 (this document) | `tnt_` |
| **Agent** | ATP-1 (this document) | `agt_` |
| **Number** | ATP-18 | `num_` |
| **Call** | ATP-4 | `call_` |
| **Message** | ATP-10 | `msg_` |
| **Conversation** | ATP-15 | `conv_` |
| **EvidencePack** | ATP-26 | `evp_` |
| **Brand** | ATP-20 | `brn_` |
| **KYACert** | ATP-22 | `kya_` |

Implementations MAY define additional internal resource types but MUST NOT extend the public ATP resource taxonomy without a successor RFC.

Each resource type is described conceptually here; full schema, lifecycle, and state-machine specifications appear in the indicated RFC.

### 5.1 Tenant

A Tenant resource represents the accountable real-world entity (§4.2). Required fields: `tenant_id`, `legal_entity_name`, `jurisdiction` (ISO 3166-2), `kyc_level`, `kyc_verified_at`, `created_at`. Optional: `display_name`, `contact_email`, `billing_reference`, `metadata`.

### 5.2 Agent

An Agent resource represents one AI persona under a Tenant. Required: `agent_id`, `tenant_id`, `display_name`, `persona_hash` (SHA-256 over canonical persona configuration), `created_at`, `first_active_at`. Optional: `voice_tier`, `voice_id`, `allowed_call_categories`, `model_class`, `metadata`.

### 5.3 Number, Call, Message, Conversation, EvidencePack, Brand, KYACert

These are introduced here only by name and identifier prefix. Full schemas appear in their respective RFCs.

## 6. Identifier formats

### 6.1 Opaque local identifiers

Resource identifiers within an ATP gateway are opaque strings matching the regular expression:

```
^[a-z]{3,5}_[A-Za-z0-9]{12,32}$
```

The prefix (3-5 lowercase letters followed by an underscore) identifies the resource type (§5). The suffix is opaque to consumers — gateways MAY use UUIDs, ULIDs, hashed values, or any other scheme that yields ≥ 64 bits of entropy and is unique within the gateway.

Examples:

```
tnt_acmehealthllc01
agt_aria
num_4155550123
call_abc123def456
msg_x9y8z7w6v5u4
conv_intake7d8e9f0a
evp_2026q1audit
brn_aria_health_brand
kya_7c4f9a3e1d8b2c5a
```

Implementations MUST treat the suffix as opaque. The character class `[A-Za-z0-9]` is normative; the use of underscores, hyphens, or other separators within the suffix is NOT permitted in v1.

### 6.2 Canonical URL form

For cross-gateway, cross-document, and audit-trail references, ATP defines a canonical URL form for every resource:

```
https://<gateway-host>/v1/<resource-type-plural>/<resource_id>
```

Examples:

```
https://gateway.agentlyne.ai/v1/agents/agt_aria
https://gateway.agentlyne.ai/v1/calls/call_abc123def456
https://gateway.agentlyne.ai/v1/conversations/conv_intake7d8e9f0a
```

Canonical URLs MUST be HTTPS. Gateways MUST publish these URLs for at least the lifetime of the resource plus any compliance-retention window declared in ATP-26 (Evidence Pack Schema).

### 6.3 DID form (optional)

For Issuer identifiers in attestation envelopes (per ATP-22), ATP uses W3C DIDs. The recommended DID method for v1 is `did:web`. Example: `did:web:agentlyne.ai`.

DIDs are not required for other resource types in v1. A future RFC MAY introduce DID-based agent identifiers for fully-decentralized deployments.

### 6.4 E.164 phone numbers

Phone numbers throughout ATP are represented in E.164 format with a leading `+` and 8-15 digits total. Examples: `+14155550123`, `+442071838750`, `+819012345678`.

Phone numbers are NOT considered ATP resource identifiers; the corresponding ATP resource is a Number (`num_*`).

## 7. Time and date encodings

### 7.1 Two encodings, contextual

ATP uses two time encodings, selected by context:

- **ISO 8601** (RFC 3339 profile, UTC, with `Z` suffix) for all JSON-encoded interfaces: tool inputs/outputs, REST resources, event payloads, dashboard projections. Example: `2026-05-23T14:23:09Z`.
- **Unix epoch seconds** (integer) for all CBOR/CWT/COSE-encoded interfaces: attestation envelopes, audit-log entries, KYA certs, transfer envelopes. Required by CWT (RFC 8392). Example: `1747234567`.

Implementations MUST NOT use any other time encoding (POSIX time with fractional seconds, milliseconds-since-epoch, locale-formatted strings, etc.) in normative ATP fields.

### 7.2 Timestamp claims naming

In JSON encodings, timestamp fields end with `_at`: `created_at`, `started_at`, `ended_at`, `expires_at`, `first_active_at`, etc.

In CBOR/CWT encodings, the standard CWT claim numbers are used: `iat` (claim 6), `exp` (claim 4), `nbf` (claim 5).

### 7.3 Time zones

All timestamps in ATP normative fields are UTC. Tenant-local timestamps (e.g., for TCPA quiet-hours computation per ATP-27) are computed at use-time from UTC and the tenant's declared jurisdiction.

## 8. Naming and encoding conventions

### 8.1 Identifier and field naming

- ATP field names use `snake_case` in JSON and CBOR encodings.
- ATP tool names use `dot.separated.snake_case` (e.g., `phone.dial`, `calls.send_message`).
- ATP resource type names use `PascalCase` in spec prose (e.g., "Tenant", "EvidencePack").
- Constants and enum values use lowercase strings (e.g., `"verified_business"`, `"in_progress"`).
- ATP event names use `dot.separated.snake_case` (e.g., `call.user_partial`, `message.delivered`).

### 8.2 Encodings

- **JSON** (RFC 8259) for tool calls, tool results, resource representations, event payloads, and human-readable interfaces.
- **CBOR** (RFC 8949) for attestation envelopes, audit-log entries, and any wire format where compactness or signing-friendliness matters.
- **base64url** (RFC 4648 §5) without padding for binary data embedded in JSON.
- **UTF-8** for all string content.

### 8.3 Numeric ranges

- Quantities (counts, sizes, durations) are non-negative integers unless otherwise specified.
- Costs and prices are decimal numbers in the smallest currency unit (cents for USD/EUR/GBP, yen for JPY, etc.) — NOT floating-point.
- Probabilities (e.g., confidence scores) are decimals in the closed interval [0.0, 1.0].
- Timestamps are integers (Unix seconds) or ISO 8601 strings per §7.1.

### 8.4 Locales and languages

Language tags use BCP 47 (e.g., `en-US`, `fr-FR`, `ja-JP`). Country codes use ISO 3166-1 alpha-2 (e.g., `US`, `GB`, `JP`). Subdivision codes use ISO 3166-2 (e.g., `US-CA`, `GB-ENG`).

## 9. Versioning policy

### 9.1 ATP version

The ATP protocol carries a top-level version string of the form `MAJOR.MINOR` (e.g., `0.1`, `1.0`, `1.1`). The current version is `0.1`.

- **MAJOR** versions are incremented when backward-incompatible changes are made (e.g., the removal of a required field, a change in default behavior that breaks existing clients).
- **MINOR** versions are incremented for backward-compatible additions (new optional fields, new tools, new RFCs).
- Patch-level changes (clarifications, errata) are tracked in RFC draft versions, not in the protocol version.

### 9.2 Version negotiation

ATP version is advertised in the session initialization handshake (ATP-2). Both the Agent and the Gateway declare their supported version range. The session proceeds with the highest commonly supported MAJOR.MINOR version.

### 9.3 RFC versioning

Individual RFCs carry their own draft versioning (`draft-01`, `draft-02`, ..., `v1.0`, `v1.1`). RFC numbers themselves (ATP-1 through ATP-35) are stable from first publication.

### 9.4 Capability advertisement granularity

Even within a single ATP version, gateways may implement different subsets of the RFC series. Capability advertisement (ATP-2 §5) operates at RFC-number granularity: gateways advertise the list of RFCs they implement. Agents discover supported capabilities by inspecting this list.

## 10. Conformance considerations

This RFC is a definitions document and contains no behavioral requirements that an implementation can independently satisfy or violate. Conformance to ATP-1 is achieved transitively by conforming to any other ATP RFC: any implementation that conforms to ATP-N (for N ≥ 2) necessarily uses the terminology, identifier formats, and encodings defined here.

ATP-33 (Required vs Optional Capabilities) defines the conformance tiers for which combinations of RFCs an implementation must support.

## 11. Open issues for review

The following issues are open for community input.

### 11.1 Identifier prefix collisions

Identifier prefixes (`tnt_`, `agt_`, ...) are defined here for the v1 resource set. As ATP grows, new resource types will require new prefixes. Reservation procedure for new prefixes is TBD — this RFC suggests a simple "first-come, first-served via PR against this RFC" model but a future iteration may need a more formal registry.

### 11.2 Identifier suffix length

§6.1 mandates 12-32 alphanumeric characters in the suffix. This provides ~71 bits to ~190 bits of entropy depending on length. For high-volume gateways issuing millions of `call_` identifiers daily, the higher end is recommended. Should the spec recommend a minimum length per resource type, or leave that to implementations?

### 11.3 DID method choice

§6.3 recommends `did:web` for v1. Should the spec explicitly support `did:key` for ephemeral deployments? `did:ion` for fully-decentralized deployments? The trade-off is implementation burden vs deployment flexibility.

### 11.4 Time precision

§7 mandates whole-second precision for both ISO 8601 and Unix epoch encodings. Some applications (audio frame timestamping, latency-sensitive observability) may benefit from millisecond precision. Should ATP-1 allow fractional seconds (ISO 8601: `2026-05-23T14:23:09.123Z`; CBOR: floating-point or fixed-point integer)?

### 11.5 Tenant hierarchies

§4.2 defines a flat Tenant taxonomy: every Agent belongs to exactly one Tenant, every Tenant is independent. Some enterprises will want hierarchical Tenants (parent organization → subsidiaries → departments → Agents). Should v2 introduce a Tenant hierarchy, or model that via implementation-defined `metadata` fields only?

### 11.6 Resource canonical URL hostnames

§6.2 anchors canonical URLs to `<gateway-host>`. For long-term audit references, this couples resource identity to the gateway operator's DNS continuity. Should a future RFC define a DID-anchored or content-addressed URL form for portability across gateway operator changes?
