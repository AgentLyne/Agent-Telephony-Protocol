## Abstract

This document specifies the Know Your Agent (KYA) Attestation — a signed claim binding an AI agent's runtime identity to an accountable real-world tenant, an operating record, and an issuer of record. KYA certificates ride alongside calls and messages in the Agent Telephony Protocol (ATP), complementing STIR/SHAKEN PASSporTs (RFC 8225, RFC 8588) by providing operator-level identity attestation where STIR/SHAKEN provides only carrier-level number-ownership attestation. KYA is encoded as a CBOR Web Token (CWT, RFC 8392) signed using COSE (RFC 9052), making it compact, telephony-native, and forward-compatible with the IETF STIR working group's CWT-PASSporT direction. This document defines the claim set, signature requirements, issuer trust model, transport bindings, revocation mechanism, and verification flow for KYA v1.

## 1. Introduction

### 1.1 Background and motivation

The deployment of AI-operated voice and messaging agents on the public switched telephone network (PSTN) and rich-messaging channels has accelerated through 2025-2026. Carriers, recipients, and regulators face a question that existing identity infrastructure does not answer: *who is operationally responsible for the AI agent that just placed this call or sent this message?*

The STIR/SHAKEN framework (RFC 8224, 8225, 8226, 8588) provides carrier-level attestation of caller-number authorization, but it does not identify, attest to, or bind any claim about the agent operating that number. SHAKEN level-A attestation tells a recipient that the originating carrier verified the calling party's ownership of the calling number; it tells the recipient nothing about whether the calling party is a human, an AI agent, who built the AI agent, who operates it commercially, what its operating history is, or what accountability chain leads back to a real-world entity.

This document specifies an attestation envelope that fills that gap. A Know Your Agent (KYA) certificate is a signed claim, issued by an authorized issuer, that binds an AI agent's runtime identity to:

- The agent's display identity (the name and persona surfaced to recipients)
- A cryptographic hash of the agent's persona configuration
- A legally accountable tenant entity (an LLC, corporation, sole proprietorship, or analogous structure under the jurisdiction's law)
- The tenant's Know-Your-Customer (KYC) verification status and method
- The agent's first-active date (an operating-history witness)
- A cryptographic hash of the agent's allowed capabilities
- The issuer of the attestation and the attestation's validity window

A KYA certificate carries no reputation score in this version of the specification; reputation is deferred to a successor revision (§12.2).

### 1.2 Relationship to STIR/SHAKEN

KYA is designed to be **complementary**, not competitive, with STIR/SHAKEN. The two attestations ride in the same SIP setup and answer two distinct questions:

| Question | Attestation that answers it |
|---|---|
| Is the calling number authorized for use by the calling carrier? | STIR/SHAKEN PASSporT |
| Is there an AI agent operating this number, and who is accountable for it? | KYA certificate |

A recipient gateway that supports both verifies them independently. A recipient gateway that supports only one degrades gracefully: a recipient with only SHAKEN sees a verified caller-ID; a recipient with both sees a verified caller-ID *and* a verified operator-of-record.

### 1.3 Relationship to ATP

KYA is one RFC within the Agent Telephony Protocol (ATP) series (see [ATP-SPEC.md](../ATP-SPEC.md)). It depends on:

- ATP-1 (Architecture and Terminology) for definitions of Agent, Tenant, and Gateway
- ATP-21 (STIR/SHAKEN Attestation Envelope) for the SIP-side identity envelope that KYA rides alongside
- ATP-25 (Audit Log Format) for the auditable record of certificate issuance, verification, and revocation events

KYA is implemented as a normative requirement of ATP conformance tier "+identity" (see ATP-33, ATP-35) and is OPTIONAL at conformance tier "basic."

### 1.4 Non-goals

This specification does not address:

- The mechanism by which a tenant completes KYC. KYA references the verification but does not standardize how it is performed; existing KYC providers (e.g., Stripe Identity, Persona, Onfido) are out of scope.
- The mechanism by which a recipient acts on a KYA verification result. Recipient policy (block, log, surface to user, etc.) is out of scope.
- Reputation scoring. Reputation is deferred to a successor revision (§12.2).
- Encryption of KYA payloads. KYA certificates are signed but not encrypted in this version; minimal-disclosure variants are deferred to a successor revision (§12.3).
- Mutual authentication between agents and recipients. KYA is a one-way attestation from the caller to the called party.

## 2. Terminology and conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174).

The following terms are used throughout this document:

- **Agent** — a distinct AI runtime persona configured under a Tenant. Identified by an opaque `agent_id` string assigned by the Issuer.
- **Tenant** — the legally accountable real-world entity (natural person, LLC, corporation, or analogous structure) responsible for an Agent's behavior. Identified by `tenant_legal_entity` and `tenant_jurisdiction`.
- **Issuer** — the entity that signs a KYA certificate. An Issuer attests, by its signature, that the bound claims are true to the best of its KYC-verified knowledge.
- **Subject** — the Agent identified by the certificate. The cert's `sub` claim contains the Agent's `agent_id`.
- **Verifier** — any entity (recipient gateway, recipient carrier, recipient application, regulator) that verifies a KYA certificate's signature and claim validity.
- **KYA Certificate** — the signed CWT envelope defined in §3.
- **Persona Hash** — a SHA-256 hash over the canonical serialization of an Agent's persona configuration (system prompt, voice id, tool catalog, response style, etc.).
- **Capabilities Hash** — a SHA-256 hash over the canonical serialization of the Agent's allowed capabilities and tool catalog at issuance time.

## 3. KYA certificate format

### 3.1 Encoding

KYA certificates MUST be encoded as CBOR Web Tokens (CWT) per RFC 8392, signed using COSE (RFC 9052) in the `COSE_Sign1` single-signer form.

This document mandates CWT/COSE over JOSE/JWT for three reasons:

1. **Wire compactness.** SIP Identity headers have practical size constraints (typically ≤1500 bytes after base64 encoding). CBOR encoding produces certificates roughly 40-60% smaller than equivalent JSON encoding.
2. **Telephony-native tooling.** The IETF STIR working group is developing CWT-encoded variants of PASSporT (`draft-ietf-stir-passport-cwt`). KYA's choice of CWT aligns it with that direction and avoids divergence.
3. **Binary-friendly claims.** Persona hashes and signature material are naturally binary. CBOR represents them as `bstr` (byte strings) without base64 encoding overhead.

### 3.2 Algorithm

The signature algorithm MUST be one of:

- **EdDSA** with curve **Ed25519** (COSE alg = -8). RECOMMENDED for new deployments.
- **ECDSA** with curve **P-256** and **SHA-256** (COSE alg = -7). REQUIRED to be supported for compatibility with hardware security modules and STIR/SHAKEN signing infrastructure.

Issuers MUST advertise their supported algorithms in the published issuer metadata (§5.2). Verifiers MUST support both algorithms.

### 3.3 Protected header

The COSE_Sign1 protected header MUST contain:

- `alg` (COSE label 1): the signature algorithm identifier (-8 or -7).
- `kid` (COSE label 4): a byte-string key identifier scoped to the Issuer. Used by verifiers to select the correct verification key from the Issuer's published key set.

The protected header MAY contain:

- `typ` (COSE label 16, future use): set to the byte string `"application/kya+cwt"` to disambiguate from generic CWTs.

### 3.4 Unprotected header

The unprotected header SHOULD be empty in v1. Future revisions may add unprotected fields for routing hints.

### 3.5 Payload

The payload is a CBOR map containing the KYA claim set (see §4).

### 3.6 Validity window

A KYA certificate's validity window (the interval `[iat, exp]`) MUST NOT exceed 24 hours (86400 seconds). Issuers SHOULD use a 24-hour window by default; tighter windows are permitted at Issuer discretion. Verifiers MUST reject certificates whose `exp - iat` exceeds 86400 (§6.1 step 7).

The 24-hour limit balances two concerns: long enough that Issuers do not face unsustainable signing load, short enough that revocation has predictable real-world effect even without per-call OCSP-style queries (§7.5).

## 4. Claim set

### 4.1 Claim numbering

KYA reuses the standard CWT claim numbers from the IANA CWT Claims Registry where applicable, and uses provisional negative-integer claim numbers in the private-use range for KYA-specific claims. Upon AAIF working group adoption, KYA-specific claims will be submitted to IANA for permanent allocation.

### 4.2 Required claims

A KYA certificate MUST contain the following claims:

| Claim | CBOR key | Type | Description |
|---|---|---|---|
| `iss` | 1 (CWT standard) | tstr | Issuer DID. v1 form: `did:web:<issuer-host>`. Example: `did:web:agentlyne.ai`. |
| `sub` | 2 (CWT standard) | tstr | Agent identifier (`agent_id`) assigned by the Issuer. Opaque to verifiers. |
| `iat` | 6 (CWT standard) | uint | Issuance timestamp (seconds since Unix epoch). |
| `exp` | 4 (CWT standard) | uint | Expiration timestamp. MUST be ≤ `iat` + 86400 (24 hours) per §3 of this document. |
| `cti` | 7 (CWT standard) | bstr | Certificate identifier. Globally unique per Issuer. Used for revocation references. |
| KYA-001 | -42001 | tstr | `agent_display_name` — the human-readable display name (e.g., "Aria"). |
| KYA-002 | -42002 | bstr | `agent_persona_hash` — SHA-256 hash of canonical persona configuration. |
| KYA-003 | -42003 | tstr | `tenant_legal_entity` — exact legal name as registered in the jurisdiction. |
| KYA-004 | -42004 | tstr | `tenant_jurisdiction` — ISO 3166-2 region code (e.g., `US-DE`, `GB`, `DE`). |
| KYA-005 | -42005 | tstr | `tenant_kyc_level` — one of: `unverified`, `verified_individual`, `verified_business`, `verified_high_assurance`. |
| KYA-006 | -42006 | tstr | `tenant_kyc_method` — opaque issuer-defined identifier for the KYC method used (e.g., `stripe_identity_v2`, `persona_kyb_v3`). |
| KYA-007 | -42007 | uint | `agent_first_active` — Unix timestamp of the Agent's first operating activity under this Issuer. |
| KYA-008 | -42008 | bstr | `agent_capabilities_hash` — SHA-256 hash of canonical capabilities/tool catalog. |

### 4.3 Optional claims

A KYA certificate MAY contain:

| Claim | CBOR key | Type | Description |
|---|---|---|---|
| KYA-009 | -42009 | tstr | `agent_brand_id` — stable identifier issued by an ATP Brand Registry (ATP-20) for an RCS/RBM, iMessage Business, or WhatsApp Business brand registration. Format is defined by ATP-20; KYA Verifiers treat this value as opaque. |
| KYA-010 | -42010 | tstr array | `agent_allowed_call_categories` — declared use-case categories (e.g., `transactional`, `support`, `appointment-confirmation`). |
| KYA-011 | -42011 | tstr | `model_class` — declaration of the LLM class powering the Agent. MUST be one of: `frontier` (high-capability general-purpose), `mid_tier` (efficient general-purpose), `small` (specialized or lightweight), `unspecified`. MUST NOT include vendor-specific model identifiers. |
| KYA-012 | -42012 | tstr array | `regulatory_compliance` — array of declaration strings. Each element is either a bare flag (e.g., `"hipaa_eligible"`, `"gdpr_subject"`) or a colon-separated flag:value pair (e.g., `"eu_ai_act_registered:HIGH-RISK-2026-0042"`). |
| KYA-013 | -42013 | tstr | `revocation_url` — HTTPS URL where the Issuer publishes its revocation list (§7). If absent, verifiers SHOULD discover via Issuer metadata (§5.2). |

### 4.4 Reserved claim numbers

The following claim numbers are reserved for future use and MUST NOT be used by current implementations:

| Claim | CBOR key | Reserved for |
|---|---|---|
| KYA-101 | -42101 | `agent_reputation_score` (v2) |
| KYA-102 | -42102 | `agent_reputation_sample_size` (v2) |
| KYA-103 | -42103 | `agent_reputation_method` (v2) |
| KYA-104 | -42104 | `recipient_disclosure_preference` (v2, minimal-disclosure mode) |
| KYA-105 | -42105 | `agent_audit_root_hash` (v2, ATP-25 cross-reference) |

### 4.5 Extension claims

Issuers MAY include private-use claims in the range -65536 to -42999. Verifiers MUST ignore claims they do not recognize. Issuers SHOULD coordinate any cross-issuer extension claims through the AAIF working group.

## 5. Issuer trust model

### 5.1 Federation-ready, single-issuer in practice

This specification defines a federation-ready Issuer model. Multiple Issuers MAY exist; recipients MAY choose which Issuers to trust. In the initial v1 deployment, only AgentLyne (`did:web:agentlyne.ai`) is operating as a KYA Issuer; the federation model is specified now to avoid breaking spec changes when additional Issuers join.

### 5.2 Issuer requirements

To operate as a KYA Issuer, an entity MUST:

1. **Publish a verifiable Issuer DID.** The DID MUST resolve via the DID resolution method appropriate to its DID method. `did:web` is RECOMMENDED for v1; other DID methods MAY be supported. In v1, KYA Verifiers MAY bypass full W3C DID Document resolution and fetch the Issuer Metadata document (step 2 below) directly using the host portion of the `did:web` DID. Full DID Document resolution (locating Issuer Metadata via a `service` array entry with `type: "KyaIssuerMetadata"` in the DID Document) becomes mandatory in a successor revision of this specification.
2. **Publish an Issuer metadata document** at the well-known location `https://<issuer-host>/.well-known/kya-issuer-metadata`. The document is a JSON object containing:
   - `issuer` — the Issuer DID
   - `keys` — a JWKS-style array of public verification keys, each with a `kid` matching the `kid` used in COSE protected headers
   - `algs_supported` — array of supported algorithm identifiers
   - `revocation_url` — HTTPS endpoint serving the revocation list (§7)
   - `kyc_methods_supported` — array of KYC method identifiers the Issuer will assert
   - `audit_log_url` — optional HTTPS endpoint for ATP-25-formatted audit logs of issuance events
3. **Operate a KYC verification chain** for every Tenant to which it issues certificates. The KYC chain MUST be auditable.
4. **Operate a revocation feed** (§7) refreshed at least every 5 minutes during operating hours.
5. **Sign all certificates with keys controlled directly by the Issuer**, not delegated to Tenants. Compromise of a Tenant's systems MUST NOT compromise the Issuer signing key.

### 5.3 Issuer trust tiers

This specification defines two non-normative Issuer trust tiers that recipients MAY use to scope policy:

- **Verified Issuer.** An Issuer that has undergone review by the AAIF working group or equivalent body. The list of Verified Issuers is published at a well-known URL (TBD post-AAIF adoption).
- **Open Issuer.** Any other Issuer meeting §5.2 requirements but not yet AAIF-verified.

Recipient gateways MAY implement policy that treats Verified Issuer certificates differently from Open Issuer certificates.

### 5.4 AgentLyne as initial Issuer

For the duration of v1, AgentLyne operates as the sole reference Issuer:

- Issuer DID: `did:web:agentlyne.ai`
- Metadata: `https://agentlyne.ai/.well-known/kya-issuer-metadata`
- Revocation: `https://kya.agentlyne.ai/revocation`
- Signing keys held in an FIPS-140-2 Level 3 HSM (or equivalent) per AgentLyne's published key-management policy.

AgentLyne's status as initial Issuer is not normative. Future Issuers MUST be able to operate without dependency on AgentLyne infrastructure.

## 6. Verification

### 6.1 Verification algorithm

A Verifier presented with a KYA certificate MUST perform the following steps. If any step fails, the certificate MUST be treated as invalid.

1. **Parse the COSE_Sign1 structure.** Reject malformed CBOR or unsupported COSE tag.
2. **Extract the protected header.** Read `alg` and `kid`.
3. **Resolve the Issuer.** Parse the `iss` claim from the payload. For `did:web:<host>`, fetch the Issuer Metadata document from `https://<host>/.well-known/kya-issuer-metadata` (v1 shortcut per §5.2 step 1). For other DID methods, perform method-appropriate DID Document resolution and locate the KYA Issuer Metadata URL via the `service` array entry with `type: "KyaIssuerMetadata"`.
4. **Select the verification key.** Find the key in the Issuer's `keys` array whose `kid` matches the protected header `kid`. Reject if no match.
5. **Verify the signature.** Using the selected key and the protected algorithm, verify the COSE_Sign1 signature over the Sig_structure. Reject if verification fails.
6. **Check temporal validity.** Reject if `now < iat - 60` or `now > exp + 60`, where `now` is the Verifier's current Unix timestamp. The 60-second skew tolerance accounts for clock drift between Issuer and Verifier. Verifiers MAY tighten or loosen the tolerance per local policy, but MUST NOT exceed 300 seconds in either direction.
7. **Check expiry window.** Reject if `exp - iat > 86400` (longer than 24 hours).
8. **Check required claims.** Reject if any claim listed in §4.2 is absent or malformed.
9. **Check revocation.** Fetch the Issuer's revocation list (§7), or use a cached copy not older than the policy-defined freshness window. Reject if `cti` appears in the revocation list.
10. **Surface claims to the recipient policy engine.** A successful verification result MUST include: Issuer DID, Subject (`sub`), Tenant legal entity, Tenant jurisdiction, KYC level, Agent display name, and any optional claims present.

### 6.2 Verification result audit logging

A Verifier that maintains an audit log (ATP-25) MUST log every verification result, including:

- Verification timestamp
- Certificate `cti`
- Issuer DID
- Verification outcome (success / specific failure)
- Hash of the certificate as presented

This audit record SHOULD be retained per the Verifier's compliance retention policy.

### 6.3 Caching

Verifiers MAY cache successful verification results keyed by `cti` for up to `min(exp - now, 3600)` seconds. Cached results MUST be invalidated immediately upon a revocation list update including the `cti`.

## 7. Revocation

### 7.1 Mechanism

Issuers MUST publish a revocation list at the URL declared in Issuer metadata. The list is a CBOR-encoded array of revoked certificate identifiers (`cti` values).

The endpoint MUST support:

- **HTTPS GET** returning the current full revocation list (`Content-Type: application/cbor`).
- **Conditional GET** via `If-Modified-Since` and `If-None-Match` headers, returning 304 Not Modified when applicable.
- **HTTP caching headers** (`Cache-Control`, `Last-Modified`, `ETag`).

### 7.2 Update frequency

Issuers MUST update the revocation list within 5 minutes of any revocation event during normal operating hours. The list timestamp (signed envelope; see §7.4) MUST reflect the actual publication time.

### 7.3 Recipient caching guidance

Recipients SHOULD refresh the revocation list at least every 5 minutes for active verification paths. Recipients MAY refresh more frequently if policy demands it (e.g., high-stakes call categories).

Recipients SHOULD NOT cache a revocation list older than 1 hour.

### 7.4 Signed revocation list

The revocation list response MUST itself be a COSE_Sign1 envelope signed by the Issuer using one of the algorithms specified in §3.2, with a `kid` in the protected header resolvable via the Issuer's published key set (§5.2). The envelope carries:

- `iss` — the Issuer DID (CWT claim 1)
- `iat` — list publication timestamp (CWT claim 6)
- `exp` — list expiration timestamp (CWT claim 4); SHOULD be no more than 1 hour after `iat`
- `revoked_certs` (KYA-201, CBOR key -42201) — array of revoked `cti` byte strings
- `revocation_reasons` (KYA-202, CBOR key -42202) — optional map keyed by `cti`, valued with a reason string

### 7.5 Implementation note

Short-TTL (24h) certificate lifetime combined with frequent revocation feed updates provides the security property recipients need without requiring online revocation check (OCSP-style) per call. Recipients SHOULD prefer the cached signed revocation list over per-call OCSP-style queries.

## 8. Transport bindings

### 8.1 SIP Identity header

For voice calls, the KYA certificate is carried in a SIP `Identity` header value with `info` parameter:

```
Identity: <base64url-encoded COSE_Sign1>;
          info=<https://agentlyne.ai/.well-known/kya-issuer-metadata>;
          alg=ES256;
          ppt=kya
```

The `ppt` (PASSporT type) parameter value `kya` distinguishes KYA from STIR/SHAKEN PASSporTs. SIP entities supporting both will see two `Identity` headers: one with `ppt=shaken` (SHAKEN) and one with `ppt=kya` (KYA).

### 8.2 SMS / RCS headers

For SMS and MMS messages, the KYA certificate is conveyed as a SIP-MESSAGE Identity header following the same format as §8.1. For RCS messages, the certificate is carried in an RBM brand context envelope (TBD coordination with Google RBM team).

### 8.3 ATP event metadata

In ATP-5 (Call Events Vocabulary), the `call.ringing` event MUST include a `kya` field when the call carries a KYA certificate:

```json
{
  "event": "call.ringing",
  "call_id": "call_abc123",
  "from": "+14155550987",
  "to": "+14155550123",
  "attestation": { ... },
  "kya": {
    "present": true,
    "verified": true,
    "issuer": "did:web:agentlyne.ai",
    "agent_display_name": "Aria",
    "tenant_legal_entity": "Acme Health LLC",
    "tenant_jurisdiction": "US-DE",
    "tenant_kyc_level": "verified_business",
    "agent_first_active": "2026-05-14"
  }
}
```

### 8.4 HTTP side-channel fetch

For environments where the KYA certificate cannot be conveyed in-band (e.g., severely constrained SIP networks), Issuers MAY publish certificates at:

```
https://<issuer-host>/.well-known/kya/cert/<base64url(cti)>
```

The fetched response is the bare CBOR-encoded COSE_Sign1 envelope. This mechanism is OPTIONAL.

## 9. Privacy considerations

A KYA certificate, when verified, reveals to any intermediary and any recipient:

- The legal name and jurisdiction of the Tenant
- The Agent's display name
- The Tenant's KYC verification level
- The Agent's first-active date

For some call categories (verified business outreach, regulated B2B communications) this disclosure is desired. For other categories (B2C personas, consumer-facing AI characters, calls where the Tenant is a private individual), the disclosure may exceed what the Tenant wishes to share.

This version of KYA defines no minimal-disclosure or encrypted-payload mode. A future revision (KYA-104 reserved in §4.4) will specify recipient-encrypted variants. Until then, Tenants who require lower disclosure SHOULD NOT use KYA. A pseudonymous variant of KYA is not viable within the current claim set because the `tenant_legal_entity` and `tenant_kyc_level` claims presuppose a verified real-world Tenant; the minimal-disclosure work in a successor revision will address this gap directly.

Issuers MUST NOT include personally identifying information about the Tenant's principals (e.g., directors, beneficial owners) in any KYA claim. Tenant-level claims describe the entity, not the natural persons behind it.

## 10. Security considerations

### 10.1 Issuer key compromise

Compromise of an Issuer's signing key allows an attacker to forge KYA certificates that recipients will treat as valid. Issuers MUST:

- Store signing keys in tamper-resistant hardware (FIPS 140-2 Level 3 HSM or equivalent)
- Operate a key rotation schedule no longer than 90 days
- Publish a key compromise response procedure in Issuer metadata
- Be prepared to revoke all certificates signed by a compromised key (via large-scale revocation list updates)

### 10.2 Tenant compromise

Compromise of a Tenant's account at an Issuer allows an attacker to operate Agents under a verified Tenant identity. KYA does not detect Tenant compromise; this remains an Issuer operational responsibility (account-takeover monitoring, anomaly detection, KYC re-verification).

### 10.3 Replay

KYA certificates have a 24-hour validity window. Within that window, the same certificate is presented on every call/message from the Agent — this is by design (the certificate identifies the Agent, not the call). Replay protection at the *call* level is the responsibility of the underlying STIR/SHAKEN PASSporT (which is per-call). KYA replay across calls is not a meaningful attack: the only thing replayed is the operator-identity attestation.

### 10.4 Cross-issuer attacks

A malicious Issuer could issue certificates attesting to false Tenant identities. Mitigations:

- Issuer trust tiers (§5.3) let recipients differentiate Verified Issuers from Open Issuers
- Recipients MAY policy-restrict to specific Issuers
- The AAIF working group is the natural forum for Issuer accreditation and de-listing of misbehaving Issuers

### 10.5 Certificate enumeration

The HTTP side-channel fetch mechanism (§8.4) exposes a URL pattern. Issuers MUST NOT allow certificate enumeration (e.g., by sequential `cti` guessing). `cti` values MUST be sufficiently random (≥ 128 bits of entropy).

### 10.6 Header stripping

A malicious intermediary may remove the SIP Identity header carrying the KYA certificate (§8.1), causing recipients to see no KYA at all. KYA does not provide standalone protection against this; the underlying SIP integrity model applies. Mitigations:

- Recipients SHOULD treat the *absence* of a KYA certificate as policy-significant for high-stakes call categories (regulated verticals, large-value transactions, sensitive personal communications).
- Verifying gateways SHOULD cross-check expected KYA presence against the originating carrier's STIR/SHAKEN attestation level — calls bearing level-A SHAKEN from a carrier known to be Issuer-affiliated but lacking a KYA header SHOULD be flagged for policy review.
- Long-term mitigation lives at the carrier interconnection layer, outside the scope of this document.

### 10.7 Algorithm downgrade

An adversary with header-modification capability could attempt to force a Verifier to accept a certificate signed with a weaker algorithm than the Issuer normally uses, or to substitute a certificate from an attacker-controlled "shadow" Issuer that supports only weak algorithms. Mitigations:

- Verifiers MUST consult the `algs_supported` array in the Issuer's metadata (§5.2) and reject any certificate whose `alg` is not listed there.
- Issuers SHOULD list only the algorithms they actively use in `algs_supported`; deprecated algorithms MUST be removed from the list rather than retained for backward compatibility.
- Recipients SHOULD maintain a local policy minimum (e.g., reject ES256-only Issuers if local policy requires EdDSA).

## 11. IANA considerations

This document requests, upon AAIF working group adoption, the following IANA allocations:

### 11.1 CWT Claims Registry

Permanent claim numbers for KYA-001 through KYA-013 listed in §4.2 and §4.3, replacing the provisional negative-integer values in the -42001 to -42013 range.

### 11.2 COSE Header Parameters

Confirmation that `typ` (COSE label 16) usage with value `application/kya+cwt` is permitted (no new allocation needed).

### 11.3 PASSporT Types Registry

Registration of `kya` as a new PASSporT type for SIP Identity header `ppt` parameter usage (§8.1).

### 11.4 Well-known URIs

Registration of:

- `/.well-known/kya-issuer-metadata` — Issuer metadata document
- `/.well-known/kya/cert/{cti}` — optional side-channel certificate fetch
- `/.well-known/kya-revocation` (RECOMMENDED default location for revocation lists)

## 12. Open issues for review

The following issues remain open in this draft. Community input is solicited.

### 12.1 Issuer DID method portability

This draft mandates `did:web` for v1 and permits other DID methods. Should we explicitly support `did:key` for ad-hoc deployment? `did:ion` for fully decentralized issuance? Or restrict to `did:web` until federation is operating?

### 12.2 Reputation

This draft explicitly defers reputation to a successor revision. Open question: should the v2 reputation model be Issuer-assigned, externally-supplied (with the cert carrying only a reputation URL), or hybrid?

### 12.3 Minimal-disclosure mode

This draft mandates plain-text claims. Open question: should v2 add a recipient-encrypted variant where Tenant identity is revealed only to recipients possessing the appropriate decryption key? This would help privacy-sensitive deployments.

### 12.4 Relationship to draft-ietf-stir-passport-cwt

The IETF STIR working group is independently developing CWT-encoded PASSporTs. Should KYA become a `ppt` value within that framework, or remain a sibling envelope? Coordination with the STIR working group is in progress.

### 12.5 Capabilities hash algorithm

This draft uses SHA-256 for persona and capabilities hashes. Open question: should v2 require Merkle hashing over a canonical structured representation so that selective disclosure of specific capabilities is possible (e.g., proving "this agent has appointment-booking capability" without revealing the full tool catalog)?

### 12.6 Regulatory compliance claim format

The optional `regulatory_compliance` claim (KYA-012) is a comma-separated string. This is intentionally lightweight for v1. Should v2 introduce a structured representation (e.g., a CBOR map of regulation-id → registration-reference) for richer regulator queries?

### A.3 Verification trace

1. Verifier receives SIP INVITE with `Identity: ...;ppt=kya;info=https://agentlyne.ai/.well-known/kya-issuer-metadata`.
2. Verifier base64url-decodes the Identity value to obtain the CBOR.
3. Verifier parses COSE_Sign1; extracts protected header. `alg = -8` (EdDSA), `kid = h'01'`.
4. Verifier fetches `https://agentlyne.ai/.well-known/kya-issuer-metadata`; parses JSON.
5. Verifier finds key with `kid = "01"` in `keys` array; extracts public key material.
6. Verifier reconstructs the Sig_structure per COSE_Sign1 rules and verifies the Ed25519 signature. ✓
7. Verifier decodes the payload CBOR. Reads `iss`, `sub`, `iat`, `exp`, `cti`.
8. Verifier checks: `iat ≤ now ≤ exp` ✓ ; `exp - iat ≤ 86400` ✓
9. Verifier checks revocation list (cached from `https://kya.agentlyne.ai/revocation`, refreshed 3 minutes ago). `cti` not present. ✓
10. Verifier returns success: `{issuer: "did:web:agentlyne.ai", agent_display_name: "Aria", tenant_legal_entity: "Acme Health LLC", tenant_jurisdiction: "US-DE", tenant_kyc_level: "verified_business"}`.
11. Recipient gateway surfaces this to its policy engine and (if configured) to the end recipient's UI.

## Appendix B — Verification pseudocode

```python
def verify_kya(cert_bytes: bytes, now: int, revocation_cache: RevocationCache) -> VerifyResult:
    # 1. Parse COSE_Sign1
    try:
        cose = cbor2.loads(cert_bytes)
        if cose.tag != 18 or len(cose.value) != 4:
            return VerifyResult(valid=False, reason="malformed COSE_Sign1")
        protected_bytes, unprotected, payload_bytes, signature = cose.value
    except Exception:
        return VerifyResult(valid=False, reason="CBOR parse error")

    # 2. Protected header
    protected = cbor2.loads(protected_bytes)
    alg = protected.get(1)
    kid = protected.get(4)
    if alg not in (-7, -8) or kid is None:
        return VerifyResult(valid=False, reason="unsupported alg or missing kid")

    # 3. Payload
    payload = cbor2.loads(payload_bytes)
    iss = payload.get(1)
    sub = payload.get(2)
    iat = payload.get(6)
    exp = payload.get(4)
    cti = payload.get(7)
    if any(x is None for x in (iss, sub, iat, exp, cti)):
        return VerifyResult(valid=False, reason="missing required claims")

    # 4. Resolve issuer
    issuer_metadata = resolve_did(iss)
    if not issuer_metadata:
        return VerifyResult(valid=False, reason="issuer DID not resolvable")

    # 5. Select key by kid
    key = find_key(issuer_metadata.keys, kid)
    if not key:
        return VerifyResult(valid=False, reason="kid not found in issuer keyset")

    # 6. Verify signature
    sig_struct = build_sig_structure(protected_bytes, payload_bytes)
    if not verify_cose_signature(alg, key, sig_struct, signature):
        return VerifyResult(valid=False, reason="signature verification failed")

    # 7. Temporal checks (with 60s clock skew tolerance per §6.1 step 6)
    SKEW = 60
    if now < iat - SKEW or now > exp + SKEW:
        return VerifyResult(valid=False, reason="outside validity window")
    if exp - iat > 86400:
        return VerifyResult(valid=False, reason="validity window exceeds 24h")

    # 8. Check required KYA claims
    for required_claim in (-42001, -42002, -42003, -42004, -42005, -42006, -42007, -42008):
        if required_claim not in payload:
            return VerifyResult(valid=False, reason=f"missing claim {required_claim}")

    # 9. Revocation
    if revocation_cache.is_revoked(iss, cti):
        return VerifyResult(valid=False, reason="certificate revoked")

    # 10. Success
    return VerifyResult(
        valid=True,
        issuer=iss,
        subject=sub,
        agent_display_name=payload[-42001],
        tenant_legal_entity=payload[-42003],
        tenant_jurisdiction=payload[-42004],
        tenant_kyc_level=payload[-42005],
        agent_first_active=payload[-42007],
        # ... etc
    )
```
